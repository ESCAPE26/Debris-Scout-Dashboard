# Debris Scout AI — Web Dashboard Prototype

A self-contained, browser-based mission-control dashboard that demonstrates the
**Detect → Track → Predict → Assess Risk → Plan/Avoid** pipeline for the
[Debris Scout](https://github.com/SSN2025/SSN2025-ISRO-Hackathon-Debris-Detection-)
concept: a distributed network of co-orbital sentinels that sense their local
environment and protect a high-value spacecraft from debris.

This package is the **visualization + simulated-pipeline layer** requested on
top of that project. It runs entirely in the browser — no build step, no
backend, no GPU, no real sensor hardware required.

## What this is / is not

| This prototype **is** | This prototype **is not** |
|---|---|
| A software simulation of detection, tracking, prediction and collision-risk assessment | Connected to a real camera, radar, or orbital catalog |
| A research / academic demonstration prototype | Flight-qualified or ISRO-certified |
| Built on a simplified, honestly-scoped relative-motion model | A validated SGP4 / full numerical-propagator implementation |
| A tool for explaining *how* such a system would work end-to-end | A statistically calibrated collision-probability product |

Every number on screen (positions, confidence, risk score, Δv) is generated by
the in-browser simulator. The **AI MODE: SIMULATION** badge in the header is
always shown to make this explicit.

## How to run it

1. Unzip this package.
2. Open `index.html` in any modern desktop browser (Chrome, Edge, Firefox).
   That's it — everything (Three.js is loaded from a CDN) runs client-side.
3. Click **Start Simulation**, or pick a scenario from the dropdown first.
4. Click a row in the **Detected Objects** table to inspect an object, view
   its predicted trajectory, and (if its risk is elevated) run
   **Simulate Avoidance**.
5. Try **DEMO MODE** in the scenario dropdown for the scripted end-to-end
   walkthrough (detect → track → predict → risk escalates to RED → maneuver
   proposed automatically).

No install, no `npm install`, no server. If you want to host it, any static
file host (GitHub Pages, Netlify, `python -m http.server`) will work.

## Pipeline mapped to files

Everything lives in `app.js`, organized into the same logical stages as the
assignment brief and the original Debris Scout architecture:

```
generateScenario()          Sense  — synthetic debris population per scenario
stepSimulation()            Sense/Detect — simulated camera+radar measurement,
                             noise injection, missed detections, false contact
alpha-filter fusion         Track — simplified Kalman-style fusion of noisy
  (in stepSimulation)        measurements into a persistent per-object state
                             (stand-in for the UKF fusion described in the
                             original repo's architecture doc)
propagateState()            Estimate/Predict — physics baseline: linear
                             in-plane motion + closed-form cross-track
                             harmonic term at the orbital mean motion
mlResidual()                Predict (ML layer) — small deterministic
                             "learned residual" layered on the physics
                             baseline, shown as the dashed prediction line
assessRisk()                Assess Risk — samples the predicted trajectory,
                             finds closest approach, converts distance +
                             closing speed into a 0–100 risk score and a
                             GREEN/YELLOW/ORANGE/RED category
openManeuverModal()          Plan — candidate radial Δv sized to add
                             clearance by the time of closest approach;
                             shows before/after risk and miss distance
render3D() / drawTrajectoryGraph()  Visualization — Three.js orbit view and
                             a 2D range-vs-time prediction graph with an
                             uncertainty band that widens with horizon
```

## Honest limitations (please read before presenting this)

- **Relative-motion model is simplified.** In-plane (radial/along-track)
  motion is propagated as locally linear; only the cross-track channel uses
  the exact closed-form harmonic solution. This is a reasonable first-order
  approximation over the short (≤5 minute) look-ahead used here, but it is
  **not** a full Clohessy-Wiltshire / SGP4 propagator, even though the
  original repository's architecture calls for one. Swapping in a real CW or
  SGP4 propagator would be a natural next step (see `propagateState` in
  `app.js` for the single function to replace).
- **No trained ML model.** `mlResidual()` is a deterministic, illustrative
  stand-in for a learned trajectory-correction network — no data collection
  or training happened. It exists to make the "physics + ML residual"
  architecture visually and structurally legible, not to claim predictive
  skill.
- **No real sensors.** Detection confidence, radar range/Doppler, and camera
  bounding boxes are not modeled here as raw sensor data — this dashboard
  works one level up, on top of already-fused object states, to keep the
  demo runnable anywhere with zero setup. The companion C++ modules in the
  original repository (`src/perception`, `src/sensors`, `src/tracking`) are
  where real YOLO-based detection and radar signal processing belong; this
  dashboard is the visualization/orchestration layer that would sit on top
  of their outputs.
- **Risk score is a prototype heuristic**, not a Foster-1992 / B-plane
  collision probability (the original repo's docs correctly name that as the
  target method). It is explicitly labeled "risk score," never "collision
  probability," for that reason.
- **Maneuver simulation is illustrative.** It nudges a velocity component and
  recomputes the same simplified physics model — it does not run a
  Sequential Convex Programming optimizer or model real thruster constraints.

## Relationship to the existing Debris Scout repository

The existing repo (`SSN2025/SSN2025-ISRO-Hackathon-Debris-Detection-`) is a
C++/CMake project defining sensor, perception, tracking, orbital-dynamics,
conjunction-analysis, and propulsion modules for a terrestrial HITL
prototype, with a **planned** CesiumJS web dashboard (referenced in its
`docs/architecture.md` but not yet implemented in the repo at the time this
was built). This package delivers that missing dashboard layer as a
standalone, dependency-free demonstration you can open immediately, using
terminology and a pipeline shape consistent with that repo's architecture
(sentinels, sensor fusion, conjunction/risk, maneuver simulation) so the two
can be presented together or the dashboard's simulated pipeline can later be
wired to real outputs from the C++ modules over an API.

## Suggested next steps for a fuller integration

1. Replace `propagateState` with calls to the repo's actual orbital-dynamics
   module (Clohessy-Wiltshire relative motion) via a small API layer.
2. Replace the synthetic scenario generator with real detections from the
   repo's YOLOv8 perception module and TI IWR6843 radar interface (or their
   simulators).
3. Replace `assessRisk`'s heuristic with the repo's Foster-1992 B-plane
   collision-probability method, and label the UI accordingly once that is
   wired in.
4. Serve object/track/risk state over a WebSocket so this dashboard becomes a
   live client instead of a self-contained simulator.
